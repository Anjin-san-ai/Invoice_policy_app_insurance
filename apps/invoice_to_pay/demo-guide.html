CMP-UC-002 · Agentic AI prototype

Automated Invoice & Outlay Validation

UK insurance claims finance teams pay thousands of supplier invoices a month — garages, hire car firms, medical providers — and check each one by hand against a contracted rate card. This demo shows a network of twelve cooperating AI agents doing that checking, paying the clean invoices automatically, and handing a human only the ones that genuinely need judgement — with every decision written to an audit trail that cannot be edited.

12 LLM agents + 1 shared coded tool Neuro SAN orchestration React + FastAPI walkthrough UI Hash-chained audit log 15 measured evaluation metrics

1 The problem, in one paragraph

Why this use case is worth automating at all.

A customer crashes their car. The insurer authorises a repair and a hire car. Weeks later, invoices arrive from a garage and a hire company — by email, by portal, as PDFs of wildly different layouts. Somebody in finance has to open each one and ask: is this the right claim? is this covered by the policy? did we authorise this much? and is the rate the one we actually contracted?

Most invoices are fine. The value is in catching the few that aren't — 14 days of hire car billed against 10 days approved, a service charged at a rate from a superseded card, the same invoice submitted twice — before the money leaves. Checking every invoice by hand to catch the small minority is slow, inconsistent, and doesn't scale as claim volume grows.

The goal

Pay the clean invoices with no human touch. Route the problem ones to a person with the problem already diagnosed, explained, and a draft action pre-filled. Never let the machine pay itself.

2 How the demo is built: two halves

Understanding the split is the key to demoing it well — they are two views of the same process.

The brain Neuro SAN agent network

Twelve LLM agents, declared in a single HOCON file, arranged as a tree. A front man (the Invoice Orchestrator) receives the request and delegates down the chain to specialists. Each agent has a description so its peers know when to call it, and instructions telling it how to do its job.

They all share one coded tool that does the deterministic arithmetic and data lookups. The agents reason about what to check and what it means; the tool guarantees the numbers are exact. Sensitive customer data travels between them as sly_data, never through the prompt.

Registry registries/apps/invoice_to_pay.hocon

The window React walkthrough UI

Thirteen screens over a FastAPI backend, showing what a finance team would actually sit in front of: a work queue, an exceptions workspace, a payment board, supplier scorecards, rate cards, analytics, and the audit trail.

The backend runs the same pipeline logic deterministically, so the demo gives identical numbers every time and needs no LLM calls to walk through. That's deliberate: you can demo the whole business story offline, then switch to the live agent network to show the reasoning.

Every agent answers exactly one question. That's what makes the decision explainable.

The guardrail worth pointing out

Agent 8 asks whether a variance is material, not merely whether one exists. A 40p rounding difference is not a dispute. Tolerance is configured, not hardcoded — currently 5% AND £25, and a line must breach both to be flagged. That one decision is the difference between a useful system and one that floods the team with noise.

4 One invoice, end to end

The path every invoice takes. Follow this order when you demo.

STEP 1ArrivesEmail, portal or API. Channel and layout recorded.
STEP 2ReadLines, units, rates, dates extracted with a confidence score.
STEP 3RedactedEmails, phones, postcodes masked before onward processing.
STEP 4MatchedTied to a claim; unmatched ones become an exception.
STEP 5ValidatedEach line checked against the rate card in force, the policy and the authorised units.
STEP 6JudgedMaterial variance? Duplicate? High value? Decide approve / query / hold.
STEP 7AuthorisedA human signs off anything above the value threshold.
STEP 8ReleasedA different human releases the payment. Written back to the claim.
Every step writes to the audit log

Each event carries the actor, the before and after state, and a SHA-256 hash of the previous event. Change any historic record and the chain breaks visibly. The Audit Trail screen shows hash chain valid live — that is the compliance story in one badge.

5 The five exception types

A fixed taxonomy — deliberately small, so the queue stays triageable and reporting stays comparable.

  • 1 Missing or invalid identifiers — no usable claim or supplier reference.
  • 2 Failed claim matching — can't confidently tie it to a claim.
  • 3 Disputed or out of tolerance — charged more than contracted, materially.
  • 4 High value — above the threshold; a human must look, regardless.
  • 5 Policy or coverage ambiguity — unclear whether the policy covers it.

What a handler actually gets

Not “this invoice failed”. They get the reason, a plain-English explanation, the specific lines at fault, the value at risk, and a pre-drafted next action — a supplier query with the rate-card evidence already quoted, ready to send in one click.

The queue is ordered by value at risk, then age, so the biggest exposure is always on top. Executing an action marks it complete with a green tick and removes the button, so the same query can never go out twice.

7 The controls that make it safe

The part a risk or audit stakeholder will ask about first.

Segregation of duties

The identity that authorises a payment cannot release it. Attempting it is refused and the refusal itself is logged. Demo it live — it's the single most convincing moment in the walkthrough.

No double payment

Releasing an already-released payment is rejected rather than retried, so a double-click or a network retry can't pay a supplier twice. The rejection is audited too.

Privacy by default

Personal data is masked at step 3, before validation or agent reasoning sees the document. Every mask is logged with the rule that caused it, so you can prove what was hidden and why.

Human override, always

A handler can overrule any recommendation — but the reason is mandatory and the original machine recommendation is preserved alongside it. You can always reconstruct what the system advised versus what the human did.

Say this plainly

The agents never move money on their own. They decide what is true about an invoice. Two separate humans move the money, and the machine records both of them.

Evaluation harness

Fifteen metrics, each scored by an independent oracle rather than by the pipeline grading its own homework: extraction accuracy and calibration (ECE), redaction recall and false positives, claim-matching F1, re-rating arithmetic, tolerance decisions, duplicate detection, exception-reason accuracy, explanation quality and audit completeness.

Be honest about this if asked

The explanation-quality score is a 5-point rubric, not an LLM judge. It checks that an explanation names the reason, the lines, the amounts and the evidence — it does not assess whether the prose reads well. Chasing three red metrics during build is what surfaced three genuine bugs in the seed data, which is the argument for having the harness at all.

9 Running the demo

Full instructions live in apps/invoice_to_pay/run.md. This is the short version.

The UI half — no LLM keys needed

# backend (warms the whole estate at startup, ~7s)
python -m uvicorn apps.invoice_to_pay.backend.app.main:app --port 8095

# front end
cd apps/invoice_to_pay/frontend
npm install
npm run dev        # → http://localhost:5174

The agent half — needs a configured LLM provider

# serves the agent network + the nsflow inspector
python -m neuro_san_studio run --server-http-port 8081 --nsflow-port 4174

# then open http://localhost:4174 and pick:
apps/invoice_to_pay
Two things that will trip you up

The Neuro SAN server does not hot-reload agent files — restart it after editing the HOCON. And credentials come from the environment or .env only: never put a key in a HOCON file.

10 What this is not

Know these before someone else finds them. Saying them first builds credibility.

Prototype boundaries

  • All data is in memory — restarting resets the estate.
  • Data is synthetic; no real claim, customer or supplier exists here.
  • Payment and claim-system writeback are mocked adapters.
  • PDF evidence packs export as JSON; the PDF rendition is stubbed.
  • No authentication or role-based access control — identities are demo strings.

Known gaps against the specification

  • Split invoicing across multiple claims.
  • Fuzzy claim matching beyond the deterministic rules.
  • OCR bounding boxes for click-to-source evidence.
  • Retry with backoff, idempotent ingestion, dead-letter handling.
  • Extraction-template learning from corrections.
  • Rate-card selection ignores the service date, so a mid-claim card change isn't honoured.
Frame it this way

The prototype proves the decision architecture — that twelve narrow agents plus a deterministic tool can validate an invoice, explain the outcome, and keep a human in control of the money. Durable storage, real integrations and access control are engineering work on a settled design, not open questions.
